## User Request

### Requested result
Add a "save" feature so the user can save the current light settings under a chosen name from the web UI; saved named settings appear in both the web UI and the tray menu, and applying one from either surface restores those light settings. Move audio (microphone mute) settings into the web UI so the UI is not light-only. Change the tray menu's static "Muted" checkable item into a dynamic action whose label shows "Mute" when the mic is currently unmuted and "Unmute" when currently muted, with the click performing that named action.

### Explicit constraints
- Saved named settings must show up in both the tray and the web UI.
- Audio settings must live in the web UI (previously light-only surface).
- Tray mute item label is state-dependent: "Mute" shown when not currently muted, "Unmute" shown when muted; clicking executes exactly the displayed action.

### Accepted tradeoffs and residuals
- None stated for this request.

#### Precision amendment (review convergence, ROUND-6, 2026-08-16)

Pinned reading of the explicit constraint "clicking executes exactly the displayed action" (the literal reading is provably unsatisfiable): the tray mute click performs the displayed action **when the displayed state still matches the hardware truth at click time**, verified by a fresh status probe taken at action time against the premise the label displays. If the mic state flipped within the poll window — the probe reports the label's target state already reached — the click **refuses with one WARN plus an immediate status refresh** (never a wrong action), and the label redraws from fresh truth within one 2 s poll interval, after which the same click performs the displayed action.

The F24 physics that force this rule, in three sentences: the meeting-app half of every mute-everything path is a single blind F24 keystroke swept to every running meeting app, app mute state is unobservable, and the sweep is therefore a bare toggle with no absolute direction. When the label is stale inside the sub-2 s poll window, the flip was made either by a sweeping path (physical button, tray, Stream Deck — apps already carried along, so acting undoes the user's just-swept app mute) or by a mic-only path (panel card, CLI — apps never moved, so acting toggles LIVE apps to muted), and the origin is unknowable per click. Since every acting alternative has a catastrophic case in one of those branches, the unique never-wrong action is the implemented one: premise ≡ probe ⇒ fire the displayed absolute verb plus the F24 sweep; premise flipped (or no truthful direction) ⇒ refuse, refresh, and let the next poll redraw the label.

This amendment governs `traystate.go`'s `muteClick` (probe gate) and the tray menu's paint/store ordering, and README's tray section states the same contract for end users.

#### Precision amendment (review convergence, ROUND-7, 2026-08-16)

Delta review round 6 substantiated three Majors against the ROUND-6 state; all three are eliminated (not re-rejected) as follows, and the accuracy contract of record is extended accordingly.

1. **Atomic conditional mic verbs (R6-F2: probe/verb were separate daemon round-trips, so a hardware event between them re-created the double-sweep the probe gate existed to close).** The daemon's mic verb set gains `mute-if <expected>` and `unmute-if <expected>` with expected ∈ `muted`|`unmuted` (grammar pinned in `internal/proto.ParseConditionalMute`; malformed forms fall to `error: unknown command`). In ONE serveUDP step the handler reads the tracker and either — premise mismatched, including unknown — replies `flipped muted`|`flipped unmuted`|`flipped unknown` with NO HID write and NO inject, or — premise matched — performs the absolute verb AND injects one F24 meeting-app sweep in the same step, replying `ok`. `error:`-prefixed replies keep the established shapes; a failed HID write runs NO sweep (the mic never moved, so sweeping the apps alone would desync them). The conditional-verb injection deliberately bypasses the physical-press debounce gate (session-goroutine-only, and a verb-driven sweep is its own user action). The tray's `muteClick` now makes exactly ONE daemon call — `mute-if unmuted` for premise unmuted (label **Mute**), `unmute-if muted` for premise muted (label **Unmute**) — and parses `ok` (INFO + refresh), `flipped` (WARN + refresh, NO further action — this refusal IS the ROUND-6 precision-amendment semantics, now daemon-side), `error:`/transport failure (ERROR + refresh); the tray's own SendInput injector is removed from the mute-click path entirely (the daemon-side inject covers it). The ROUND-6 never-wrong rule stands unchanged; what changes is that the premise check and the action are atomic, closing the probe→event→verb window. The accepted residual floor is a physical press received at the HID level but not yet processed into the tracker when the check runs — the tracker's last processed event is the daemon's authoritative best-known state, and every sweeping path keeps tracker update and sweep in the same step.
2. **Generation-retirement settings-menu pool (R6-F1: with in-place pooled reassignment, a stale WM_COMMAND could find slot AND native title both already rebound to the new name, passing the ROUND-6 title verification).** The "Saved settings" submenu NEVER rebinds a live pooled row to a different name in place. Each rebuild (still change-gated by `traySameMenuSpecs`) is planned by the pure `trayPlanSettingsSync` (whole-spec identity matching): rows rendering unchanged specs continue with their binding untouched; every row whose spec vanished (a rename, or removal beyond the new list length) is RETIRED — command slot cleared first, title repainted to `(no saved settings)`, disabled, hidden, stamped with the retirement time; new names draw eldest-first from retired rows whose retirement age is ≥ 60 s (`trayRetireAge`), else a FRESH `AddSubMenuItem` row; the retired pool is capped (`trayRetiredCap = 32`, overflow rows stay permanently hidden/disabled/unbound — the 100-name store cap bounds live rows, and churn is gated to genuine name-set changes). The ROUND-6 click-time native-title verification stays as a second layer. A rename during the same second therefore leaves the OLD row invisible/disabled/cleared — a click dispatched from the pre-rebuild display finds an unbound slot (or a placeholder title) and no-ops — and a ≥ 60 s-old retired row may be reused, a gap no queued WM_COMMAND can bridge.
3. **Armed-title verification (R6-F3: a failed native `SetTitle`/`Enable` left the visible label ≠ the armed premise, so a premise-matching click could execute the opposite of the displayed verb).** After painting the mic item's title and enablement each tick, the refresh loop reads the row back via `GetMenuItemInfoW` (MIIM_STRING title + MIIM_STATE `MFS_DISABLED`; shared reader `trayMenuItemNativeState` behind both settings-row and mic verification) and stores the armed snapshot ONLY when the native read-back exactly matches the painted title AND the expected enablement (`trayArmedMatchesNative`); on any mismatch the snapshot stays at the last verified paint (which still matches what is on screen), one WARN is logged, and the 2 s poll retries — self-healing. The click additionally re-verifies the live native row against the loaded snapshot before its one conditional daemon call; a mismatch is a WARN + refresh no-op. On non-Windows builds the verify helper is a `true` stub (state updates are Go-side and serialized on the refresh goroutine; the library logs native failures — the portable residual, accepted).

This amendment governs `internal/proto` (conditional-verb grammar), `internal/daemon` (`conditionalMute`), `traystate.go` (`muteClick`, `trayMuteConditionalVerb`, `trayPlanSettingsSync`, `trayArmedMatchesNative`), `traystate_test.go`, `tray_other.go` (portable stubs), and `tray_windows.go` (shared native reader, retirement glue, armed-verify gating); README's daemon and tray sections state the wire verbs and the same contract for end users.

#### Precision amendment (review convergence, ROUND-9, 2026-08-16)

Delta review round 8 substantiated one Critical plus four Majors against the ROUND-8 state; all five are eliminated as follows, and the accuracy contract of record is extended accordingly.

1. **Full-buffer datagram rejection (R8-F1, Critical: headroom alone could not stop truncation from manufacturing a valid shorter command).** The ROUND-8 argument — "a >128-byte datagram truncated on Unix still leaves a >42-byte surviving name" — was false for PADDING attacks: `light settings delete ` + 100 spaces + `target` + a >128-byte suffix truncates at the buffer into exactly the delete prefix, padding, and a VALID shortest name; `TrimSpace` plus the settings handler's raw-suffix name re-read collapse the padding, and the daemon deleted the existing `target` setting. The rule is now size-keyed, not content-keyed: the largest legal wire command is exactly 64 bytes (22-byte delete prefix + 42-byte name cap), so `serveUDP` refuses ANY read that fills the 128-byte receive buffer with `error: command too long` and never dispatches it (no handler runs; a padded `shutdown` cannot fire the shutdown hook either). Legal sizes are untouched: 63/64-byte deletes act normally end-to-end, and a 65-byte delete still arrives whole and draws the store's documented `error: settings name too long (max 42 bytes)`; on Windows an oversized read still fails (WSAEMSGSIZE — logged, survived, client sees a timeout). Wire test (real socket pair, real store handler): the 100-spaces pad attack is refused and `target` survives; an exactly-128-byte padded `status` is refused by the size rule alone; 64- and 65-byte commands keep their established replies.
2. **Tracker-unknown on undecodable event and on reconnect (R8-F2: tracker staleness poisoned conditional-verb premises).** Two reset paths now keep the tracked mute state premise-worthy or `unknown`, never silently stale. (a) A physical `0x21` press whose value byte does not decode means the mic moved but the direction is unreadable: `handleEvent` resets the tracker to UNKNOWN (conditional verbs refuse `flipped unknown` instead of acting on stale belief) while the legacy F24 sweep STILL runs — that sweep fired on undecodable presses since before conditional verbs existed, and suppressing it would silently change the physical button's meeting-app behavior. (b) `Run` resets the tracker to UNKNOWN the moment a new device session binds (`SetDevice` point, under `opMu` per R7-F1's uniform rule): there is no readable state query and the handshake does not report the state, so a fresh session can never inherit a dead session's belief. Tests pin: undecodable press ⇒ tracked unknown + exactly one sweep + a subsequently refused conditional; a decodable press (control) still tracks and injects; a full reconnect cycle (`unmute` on session 1, read error, re-handshake on session 2) ⇒ `status` unknown ⇒ `mute-if unmuted` replies `flipped unknown` with zero injections — and a real press on the new session re-establishes truth so conditionals act again.
3. **Printable-only name grammar (R8-F3: NUL/control bytes broke the name across surfaces).** `validateSettingsName` now rejects EVERY byte below `0x20` (NUL, newline, tab, CR, ESC, …) and `0x7F` (DEL) with the established `error: invalid settings name`, byte-wise: multi-byte UTF-8 continuation bytes are all ≥ `0x80`, so printable unicode names (CJK, emoji, accented text) remain legal. The two guarantees bought: every accepted name is exactly ONE line of the newline-joined list reply (no name can forge list lines), and every accepted name is Windows-UTF16-representable (`syscall.UTF16PtrFromString`'s EINVAL on an embedded NUL can never fire on the tray's menu paths). The load side enforces the identical grammar via the shared name predicate, so a file containing a control-byte name classifies corrupt exactly like a newline-bearing one. Tests pin NUL/tab/newline/CR/ESC/DEL rejected identically for save/apply/delete with the grammar error, nothing landing in the store, and a store full of legal unicode names listing byte-exactly across save → list → reload.
4. **Vendored systray with synchronized callback bindings (R8-F4: the tray bound menu-item click handlers into the fork's plain `click` field while the Win32 pump was already dispatching it — a formal data race the ROUND-6/7 ordering discipline could only time around).** ROOT-CAUSE: `github.com/energye/systray` v1.0.3 is vendored at `third_party/systray` (full copy: `go.mod` unchanged, `LICENSE`, all platform files) with `replace github.com/energye/systray => ./third_party/systray` in the root `go.mod`; imports stay unchanged. The one patch class (documented precisely in `third_party/systray/PATCHES.md`): every callback binding a native dispatch loop reads — `MenuItem.click` (the flagged one: written by `Click`, read by `systrayMenuItemSelected` on the Windows `WM_COMMAND` path / darwin export / unix dbus handler), plus the direct equivalents `winTray.onClick/onDClick/onRClick`, the darwin package-level `onClick/onDClick/onRClick`, and the unix `usni.activate/dActivate` — becomes `atomic.Pointer[...]` with atomic stores in the setters and paired getters at every dispatch read site. Fields that do not share the post-pump-write/pump-read shape (title/tooltip/disabled — rendered through winapi/native toolkits from the caller goroutine; dispatch-side bookkeeping read only on the dispatch goroutine) are deliberately untouched. The tray's go:linkname targets (`menuItems`, `menuItemsLock`, `wt` and the `winTray` prefix mirror through `menuOf`/`muMenuOf`) are unchanged by the patch and `build.sh` proves the windows build still links them; the existing bind-immediately + native-verify discipline stays as belt-and-suspenders on top.
5. **Save-side invariant validation (R8-F5: save could persist values load would refuse, writing a self-corrupting file).** The store's validity invariants are factored into shared predicates — `validStoreName` (trimmed-form-equal + the name grammar), `validSavedSetting` (non-empty `Lights`), and `validSavedLight` (0 ≤ `Brightness` ≤ 100, `TempByte ≤ maxTempByte`, `portPattern` key) — run by BOTH `NewSettingsStore` load and `SettingsStore.Save`, so the two sides can never drift. A save whose candidate violates them (reachable live: the CCT parser feeds inbound pwr/brightness/temp bytes through unchecked, so a garbage or foreign firmware broadcast can drive `State` out of range) is refused with `error: live state violates the saved-settings invariants (brightness 0-100, temp step, COM key, name grammar); refusing to save`; NOTHING is persisted and the store is unchanged — the alternative was a file the next load classifies corrupt, taking the whole store with it. Tests pin: every violation class refused at the store with the file byte-for-byte frozen and the list unchanged, and the live path end-to-end (out-of-range inbound frame ⇒ refused save ⇒ no file written ⇒ valid frame ⇒ the retry saves).

- Produces (fixed by contract §1):

```go
type SavedLightState struct {
    On         bool `json:"on"`
    Brightness int  `json:"brightness"`
    TempByte   byte `json:"temp_byte"`
}

type SavedSetting struct {
    Lights map[string]SavedLightState `json:"lights"` // key: COM port path ONLY (registry names are mutable and never key entries)
}

const maxSettingsCount = 100                           // hard cap; a NEW name past the cap is refused

type SettingsStore struct { /* unexported: mu sync.Mutex, path string, byName map[string]SavedSetting, corrupt bool */ }

func NewSettingsStore(path string) *SettingsStore      // "" path -> disabled store; loads; missing file -> empty; CORRUPT/UNREADABLE file -> disabled-corrupt store
func (s *SettingsStore) Enabled() bool                 // false when disabled OR disabled-corrupt
func (s *SettingsStore) Save(name string, snap SavedSetting) error // overwrite by exact name; error = cap/persistence/corrupt refusal, store left unchanged
func (s *SettingsStore) Delete(name string) error      // unknown name or disabled/corrupt store -> error, store left unchanged
func (s *SettingsStore) List() []string                // sorted names; empty when disabled or disabled-corrupt
func (s *SettingsStore) Get(name string) (SavedSetting, bool)
```

- Produces (wire verbs, contract §3 — literal replies):
  - `settings save <name>` → `saved "<name>" (N lights)` (N = SAVED known-state lights); failures `error: settings save failed: <err>` (persistence), `error: no known light state to save`, `error: too many saved settings (max 100)` (a NEW name when the store already holds `maxSettingsCount = 100` entries — overwriting an existing name always fits)
  - `settings list` → sorted names newline-joined; empty store → `""` (the wire contract for "none"); a disabled store replies `error: settings persistence disabled` and a disabled-corrupt store replies `error: settings store corrupt or unreadable: <path>` — the same single-line `error:` shape, so every client parses it with the existing error:-prefixed ⇒ not-ok rule (F5)
  - `settings apply <name>` → one line per entry in the fleet fan-out shape `COM4 desk: on 47% 2900K`; failure shapes `error: light "<key>": unreachable, skipped`, `error: unknown setting "<name>"`, `error: no lights connected`
  - `settings delete <name>` → `deleted "<name>"`; failures `error: unknown setting "<name>"` (name validation identical to save/apply)
  - Validation/disabled: `error: invalid settings name`, `error: settings name too long (max 42 bytes)`, `error: settings persistence disabled`, `error: settings store corrupt or unreadable: <path>`, plus a usage error for malformed sub-verbs.

**Behavior:**
1. Persistence: the store lives at `<stateDir>/light-settings.json` beside the existing registry/state files, mirroring names.go conventions (`json.Marshal` + `MkdirAll` + 0644 perms, in-memory mutex); a missing file defaults to empty; a CORRUPT or UNREADABLE file at load makes the store DISABLED-CORRUPT — save/apply/delete AND list reply `error: settings store corrupt or unreadable: <path>`, and NO save ever replaces the corrupt file (the recovery procedure is stop the daemon -> rename/delete the file -> start the daemon, matching Task 7's file note and the runbook); an empty `stateDir` disables the store, wired inside `NewMultiManager` with NO signature change. One deliberate deviation from the non-atomic `os.WriteFile` Registry idiom: the write is a write→close→replace sequence — marshal, write a temp file IN stateDir to completion and CLOSE it, then a same-volume replace over the target (`os.Rename`; on Windows `os.Rename` is MoveFileEx with REPLACE_EXISTING — this does NOT claim a Windows rename is atomic). A crash at any point in the sequence leaves either the intact OLD store or the intact NEW store, plus possibly an orphan .tmp — never a truncated store. The safety argument is the write→close→replace ORDER, portable across platforms; Linux tests cannot expose platform rename semantics, so the claim rests on that ordering alone (F3): saved settings are user-recalled data and a torn or failed whole-file rewrite must never silently lose every saved name.
2. Save: `settings save <name>` snapshots the same LIVE-CONNECTED light set the fleet fan-out enumerates — the session set behind `handleAll` filtered by a NONBLOCKING live-link predicate (shipped: `Manager.liveLink()`, a `TryLock` on the per-light mutex answering "port != nil RIGHT NOW"; per-light `Manager.Connected()` is explicitly REJECTED because it can block behind a wedged write, F4; on a TryLock miss the light reads as not-live rather than stalling the UDP loop) — keeping only lights whose state is KNOWN via `State.Status()`'s known flag (the fourth return value: a connected light is deliberately unknown after daemon restart until an echo or knob event, and snapshotting an unknown light would record invented defaults instead of the current hardware look). All reads are memory-only state reads (`Status()`/`TargetOn()`) so a wedged light cannot stall the UDP loop, keying each entry by its COM PORT PATH ONLY — registry names are mutable via `light name`/`light unname` and must never decide which hardware an entry restores; an off light saves its restore-target brightness, not 0. Unknown-state lights are OMITTED, and a disconnected light whose state is merely CACHED is excluded (R3-F1: exclusion needs BOTH conditions — no session in the enumerated set at all AND, for a session RETAINED across a rescan miss whose port is nil/never-opened, rejection by the live-link predicate — and in neither case is it counted in the reply's N); when ZERO lights have known state the reply is `error: no known light state to save` and NOTHING persists (the store stays untouched). `saved "<name>" (N lights)` counts the SAVED (known-state) lights; saving an existing name overwrites it; a NEW name when the store already holds `maxSettingsCount = 100` entries is refused with `error: too many saved settings (max 100)`; a persistence failure replies `error: settings save failed: <err>` and leaves the store unchanged — the in-memory entry commits only after the write→close→replace sequence succeeds (F3).
3. Name validation (identical for save, apply, and delete; names are TRIMMED AT THE PIPELINE BOUNDARY — `serveUDP` and `HandleCommand` TrimSpace the command before the settings handler ever sees it, and the handler re-reads the name from the RAW suffix after the sub-verb so an EMBEDDED newline is not collapsed into a space by field-splitting): the STORED name is the trimmed form — internal whitespace is preserved, leading/trailing whitespace is never meaningful, and `foo ` and `foo` are the SAME setting (a later save overwrites; no distinct whitespace variants can exist, F2). Consequently empty/whitespace-only names (trimmed to empty), names containing a newline, and names case-insensitively starting with `error:` are rejected with `error: invalid settings name`; names over 42 BYTES are rejected with `error: settings name too long (max 42 bytes)` — `maxSettingsNameLen = 42`, derived as the daemon's 64 B UDP receive buffer minus the 22 B longest verb prefix `light settings delete ` (a longer name would save fine, then silently truncate on delete/apply and could never be removed or applied). A disabled store short-circuits save/apply/delete with `error: settings persistence disabled`, and a disabled-corrupt store (Behavior 1) short-circuits them with `error: settings store corrupt or unreadable: <path>` (list replies the same disabled/corrupt string either way, Behavior 4). Delete: `settings delete <name>` removes the entry and persists the store (same write→close→replace discipline as save); an unknown name replies `error: unknown setting "<name>"`; success replies `deleted "<name>"`.
4. List: `settings list` replies with the sorted names newline-joined, or the literal empty string `""` when the store is empty — `""` IS the wire contract for "none" (a zero-length UDP datagram); on a disabled or disabled-corrupt store it replies with the store's single-line `error:` string (`error: settings persistence disabled` / `error: settings store corrupt or unreadable: <path>`) — NOT an empty success — so every client parses it with the existing error:-prefixed ⇒ not-ok rule (F5).
5. Apply fan-out: `settings apply <name>` replies `error: unknown setting "<name>"` for an unknown name and `error: no lights connected` when ZERO lights are connected; otherwise entries are applied in PARALLEL exactly like the `handleAll` fan-out — goroutine per key, `wg.Wait`, each key's whole frame sequence (per Behavior 7: power-state frame always LAST) inside ONE `callLight` so a wedged light costs one 2 s `CallTimeout` once (contract §3).
6. Apply resolution and reply shape: each key IS a COM port path and resolves only against the live session on that port — NO `reg.Resolve(name)` lookup (registry names are mutable and must never redirect an entry to different hardware); a port with no live session yields `error: light "<key>": unreachable, skipped` while the rest still apply; reply lines are written into a slice PREALLOCATED in keys-sorted order so the reply is deterministic regardless of goroutine completion order, mirroring the fleet fan-out shape (`COM4 desk: on 47% 2900K` — the fleet `label` still renders display names in reply lines; identity stays port-only). Moving a light to a different USB port/COM makes its old entries report `unreachable, skipped` — the documented remedy is to re-save under a new name (delete + save).
7. Apply playback per key through the existing per-light command path (`Manager.HandleCommand`), POWER-STATE FRAME ALWAYS LAST (F5): an ON entry plays on → brightness → temp; an OFF entry plays brightness → temp → off, so the saved brightness/temp land in the light's restore-targets BEFORE the off frame parks it and a later `on` restores the saved look (the previous bare `off` kept the light's currently-disturbed restore brightness/temp instead of the saved ones). Brightness/temp writes to an OFF light briefly ENERGIZE it — firmware behavior: those writes light the lamp and NO silent alternative exists (F10) — so applying an off entry flashes the light momentarily (the fan-out is parallel, ~sub-second per light) before the off frame parks it; the off-entry frame order remains brightness → temp → off with the power-state frame always LAST, and the frame-sequence test pins exactly that order. Task 7's README documents the flash. The stored temp byte renders through `ByteToKelvin`, re-quantizing to the same step.
